# Reject overflowing client timer delays — 2026-10-18

Selected: JavaScript request timeouts must be positive finite numbers at or below 2,147,483,647 milliseconds. This is the native timer API ceiling, not a relay operating limit. [Node documents that larger delays become one millisecond](https://nodejs.org/api/timers.html#settimeoutcallback-delay-args); the [browser timer interface uses a Web IDL long delay](https://html.spec.whatwg.org/multipage/webappapis.html#windoworworkerglobalscope). The previous positive/finite check accepted overflowing values, potentially turning a long requested wait into an immediate join/request timeout and closure.

One small shared validator runs before `connect` creates its WebSocket, during direct construction, and when each serialized command starts. The existing public `requestTimeoutMs` property remains mutable; rechecking it at command start prevents a later unsafe assignment from installing a bad timer or sending the command. That local configuration error rejects the command without closing the connection, and a valid restored value permits subsequent commands. Direct construction now uses the same 10,000 ms default as `connect`. No setter state, custom timer scheduler, extra dependency or native data-path change was added.

Three regressions fail against the original client: overflowing join timeout, unchecked direct constructor input, and an overflowing property assigned after connection. The old run records Node's `TimeoutOverflowWarning` and explicitly reports the delay being set to 1. The selected tests check rejection before socket construction/listener installation or command sending, queue recovery after restoring a valid value, the inclusive maximum, positive fractional delays, and the constructor default. Fractions retain their existing acceptance; actual timing granularity still belongs to the runtime.
