# Check bridge admission limits before binding

Selected: expose validate_connection_limits(max_connections, max_connections_per_ip) -> Result<()> and call it from the bridge CLI before binding/logging. serve_with_limits uses the same helper in place of its original inline checks, preserving defensive validation for Rust embedders. The helper only checks existing bounds; it does not allocate or open a listener.

Global connection limits remain positive and at most Tokio Semaphore::MAX_PERMITS. Per-IP limits remain zero (disabled) through u32::MAX. Defaults and valid values, including 100,000 connections, are unchanged. Origin and upstream URL validation retain their existing order. No protocol, queue, timeout, per-packet branch, lock, payload ownership or new numeric policy is introduced. This is an additive public validation helper, not a replacement serving API.

Previously the CLI bound the address and logged legacy bridge listening before serve_with_limits rejected invalid connection limits. With an occupied address, the bind error masked the invalid setting. With a free ephemeral address, --max-connections 0 briefly bound and logged listening, then returned its configuration error. The shared preflight now reports the existing limit error first and emits no listening log for that rejected configuration.

A Unix real-CLI integration regression holds the requested bind address. Invalid global limits (zero and usize::MAX) and, on this 64-bit host, a per-IP value above u32::MAX must report their existing limit errors before binding. Valid pairs (1/disabled, 100,000/disabled, maximum semaphore permits/maximum per-IP value) must instead reach the deliberate bind error. No connection slots are allocated for these held-address checks. Each child has a two-second failure guard and is killed/reaped if it fails to finish. Against original runtime logic the two invalid-case methods fail; the valid-boundary method already passes.
