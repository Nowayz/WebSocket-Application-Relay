# Frontend retirement during upstream welcome — 2026-10-19

The bridge previously read only upstream traffic while waiting for its welcome ID. A legacy client could send Close or drop TCP after subscribing, yet its bridge connection, upstream socket and admission slot remained until the ten-second welcome deadline. Ping from that client also waited. Two real-socket reproducers establish that Close/EOF fail to release a bridge's only slot within a two-second watchdog before the change.

The selected welcome loop polls both peers. Frontend Ping/Pong is serviced while no application message is retained. A frontend Close is acknowledged and sent upstream with its original code/reason, without waiting for an upstream Close acknowledgement; EOF retires the connection. Error handling uses the existing mapped frame-error Close. The existing outer welcome deadline bounds this work. Upstream welcome validation, upstream failure Close mapping and forwarding semantics remain in place.

To preserve pipelined legacy commands and FIFO, the loop can retain one complete frontend application Message by moving its existing owner into an Option. It then stops frontend reads until the welcome is available. After sending the legacy ID, the forwarding loop consumes that retained message once before reading another frontend message. No payload copy or separate queue allocation is introduced. The message uses the existing 16 MiB frontend input limit; codec storage remains additional. This is bounded buffering, not a zero-memory startup path.

The tradeoff is explicit: a later Close or Ping behind a retained application message is not read during welcome; it can still wait for the existing deadline. A frontend that disappears during the earlier upstream TCP/HTTP connection attempt can also wait for that stage's own deadline. The improvement covers frontend retirement/control during the welcome read when no application message is retained, not every possible setup position. This keeps the implementation to one owned-message slot rather than a general staging queue or extra background reader.

Before: both Close/EOF regressions fail, completing their failed run in 2.00 seconds. After: both pass in 0.04 seconds, including forwarding the original normal Close/cancel join reason, upstream retirement and a subsequent valid welcome through the same one-slot bridge. A separate binary/text test gates the upstream welcome, gets a pre-welcome Pong, pipelines two application messages and verifies welcome ID first followed by the two exact replies in FIFO order. In an isolated mutation, dropping the retained message makes this test fail: the upstream receives second-π where first-π is expected. The mutation is never selected or released.

All 133 library tests pass in 10.03 seconds; the prior deliberate ten-second stalled-welcome test accounts for most of that time. Clippy with lib/tests and warnings denied passes. The JS integration suite passes all 65 checks in 1.1245 seconds of test execution and returns all six checked resource gauges to zero. Builds/install/cleanup add wall time. No 100k traffic or throughput claim is needed for this optional bridge setup change.
