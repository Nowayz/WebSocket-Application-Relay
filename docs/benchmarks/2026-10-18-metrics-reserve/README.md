# Metrics exposition capacity

Selected: initialize the metrics response String with 8,192 bytes rather than 2,500. The measured current exposition contains 7,336 bytes across 42 metrics; the old buffer grows to 10,000 bytes while the candidate stays at 8,192. This avoids growth for the current format and reduces retained response-buffer capacity by 1,808 bytes (18.08%). It is a capacity hint, not a limit: future larger responses still grow normally. No metric content, snapshot behavior, counter update or HTTP behavior changes.

The actual public `Metrics::render` operation is measured, including String construction, all atomic loads, formatting and destruction. The fixture has zero counters, 100,000 sessions and 10,000 channels. All eight output files are byte-identical. Even replacing every numeric value in this format with twenty decimal digits yields at most 8,125 bytes, below the new initial capacity. This bound describes current static exposition, not an enforced maximum.

Eight fresh pinned processes alternate control/candidate/candidate/control/candidate/control/control/candidate on CPU 8. Each records seven batches of 20,000 renders. Control process medians range 1,971.75–2,217.86 ns; candidate medians range 1,935.51–2,122.72 ns. The ranges overlap and this short run drifts over time; no CPU improvement is claimed. This is a response-buffer allocation improvement, not a relay throughput or end-to-end HTTP speed claim. No long load test is needed for this one-line capacity change.

All 91 clean library tests pass in 0.54 seconds, and Clippy passes all targets with warnings denied. The frozen benchmark builds confirm recompilation and differ only in initial capacity; the selected source additionally documents the hint. Benchmark source and control/candidate metric source snapshots are retained with build identities. The patch applies to clean base 0b531f9. Existing manual services, convenience binaries and the three protected source overlays were preserved.
