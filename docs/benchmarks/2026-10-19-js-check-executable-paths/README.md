# Reliable short JavaScript fixture checks

`scripts/check-js.sh` built with Cargo but launched hardcoded `target/debug` paths. With `CARGO_TARGET_DIR` set elsewhere, a clean snapshot reproduced a successful build followed by missing-binary failures. If default-directory executables existed, the old checker could instead launch unrelated stale binaries. The checker now reads the selected bin executable paths from Cargo's structured artifact output. The custom-target reproduction has no default-directory binary, so the successful check demonstrates use of the actual build outputs.

The same checker now runs its full suite, including the idle test, against one idle-enabled fixture instead of restarting the native relay for a second pass. The native relay has four I/O workers, and the bridge runtime has four worker threads. Readiness checks the native ready endpoint and bridge TCP listener. Before success, six gauges must be present and zero: connections, sessions, queued bytes, variable bytes, read-buffer reservation and output-queue capacity. The existing exit trap terminates and waits for the two owned fixtures on both success and failure. No production runtime or protocol changes are made.

In a clean source snapshot excluding the three pre-existing overlays, the revised custom-target invocation passes all **61 JavaScript cases in 1.122 seconds**, with zero skips and all six gauges retired. Cargo compilation and npm installation add wall time; no speedup claim is made for the suite itself. The snapshot has no `target/debug/war-relay` executable.

A negative integration check starts a real extra native WebSocket after the suite. It joins a channel and sends self-directed null messages every 100 ms to remain active under the one-second idle policy. Although all 61 tests pass, the checker correctly exits one after observing connections/sessions equal to one. Its trap then shuts down both services, the extra client exits, and all three test ports are released. The test-only npm wrapper and client remain local at `artifacts/js-check-leak-fixture`; they are not installed product tooling.

The initial readiness prototype incorrectly required a plain HTTP response from the WebSocket-only bridge and failed readiness; the accepted version uses a Bash TCP-listener probe. The initial setup command also attempted to select the snapshot as its working directory before creating it; no process ran in that failed attempt. These were fixture-development errors, not relay defects.

The supported invocation remains `./scripts/check-js.sh`; `CARGO_TARGET_DIR=/absolute/cache ./scripts/check-js.sh` is now supported correctly. Ports 19137–19139 must be free. Each run still uses the lockfile through `npm ci`. No dependency, long-lived monitor, alternate test runner, or new production configuration is introduced. The README and short-test guide document the workflow. Existing manual services, convenience release binaries and dirty source overlays remain untouched.

Compressed before/after/failure logs and executable/source identities are retained here. The reusable script itself is tracked in `scripts/`. Run `python verify.py` to audit the recorded results.
