# Client profile targets and corrected-monitor timeout recheck

Selected tooling change: `mixed-capacity.py --profile` now accepts `--profile-target server|capacity|sidecar`. Server remains the default; nondefault targets require profiling. The gated perf command targets exactly the selected child PID, recorded with its command and diagnostic scope in the receipt. Profile artifacts retain exclusive-prefix checks and cleanup. Relay and client runtime implementations remain unchanged.

A separate two-second diagnostic run uses the current native relay, 100,000 private users and 8,192 room fanout readers, 1 KiB values, four private probes/user/second and four-message fanout windows at 16 Hz. Churn workers, inspectors and extra private pairs are explicitly zero. Eight native workers and both eight-worker clients are pinned to disjoint physical CPU sets with checked per-thread affinity. The profile attaches only to the fanout sidecar after readiness and stops before teardown. It passes correctness and all 32/32 windows. Full per-user data, commands, affinity and binary hashes are retained.

The sidecar profile records 3,557 user-cycle samples with zero reported lost samples. Self sample shares include 21.85% timeout polling, 6.76% the fanout task, 6.29% I/O registration readiness, 5.82% shared-buffer drops, 4.50% timer-entry drops and 3.20% sleep polling. Symbols can include multiple monomorphizations and sampled instruction attribution; percentages are not a causal latency decomposition. Sampling and stack unwinding can perturb scheduling. This profiled run is excluded from ordinary performance comparisons. It cannot establish the server share of end-to-end delay.

The timer work motivated a limited recheck of the previously rejected one-timeout-per-reader-window client. Its first screen reduced client CPU, while the earlier full-population pair failed selection. The recheck uses the same earlier matched frozen control/candidate client pair, the current unchanged native relay and the corrected lightweight monitor. Independent churn is now explicitly disabled. Both the observer and workload differ from the old campaign; do not infer that either alone explains changes between campaigns. The older decision remains archived at [window-timeout screen](../2026-10-18-window-timeout-screen/README.md).

Four ordinary fresh processes run control/candidate/candidate/control, each with two seconds of traffic: eight measured seconds total. Setup and exhaustive teardown are outside traffic. Each holds 100,000 private users in 6,250 rooms of 16, with eight checked observations per user, and 8,192 fanout readers with 128 observations each at full offered load. No profile, build, test or compression work overlaps these runs. No TLS. Exact commands and topology are recorded.

The candidate remains unselected. Its client CPU does not establish a repeatable saving, private tails are mixed, and one candidate misses offered fanout load (31/32). The runner correctly returns overall failure while retaining `correctness_passed: true`; all child processes exit zero. Every issued payload/sender/FIFO check and exact lifecycle/message/byte reconciliation passes, routing-copy counters remain zero, and final connection/session/queue/read-storage gauges return to zero. The missed-load trial has 124 fanout observations per reader, not 128. CPU values cover the existing ready/measured gates, including settling. These finite observations cannot establish a long-term per-user p99 or latency SLA.

The new profiling flag is verified live for all three targets. Sidecar uses the full-population run; default server and explicit capacity use two-second 32-user/16-reader fixtures. Both small fixtures meet 2/2 windows. Invalid nondefault-without-profile and unknown target selections return argument error before creating output. Existing six clock/descriptor tests and artifact-collision checks pass. Profile output is kept outside ordinary timing evidence.
