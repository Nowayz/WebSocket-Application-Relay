# JavaScript final-close handler cleanup, 2026-10-19

Source base `690ba90`. Selected fix: remove the Relay client's live WebSocket message and close handlers when the socket's final close event arrives, before rejecting pending work and notifying Relay close subscribers. Only the two library-owned handlers are removed. Caller-installed WebSocket listeners remain. Pending command rejection, queued-command refusal after closure, close code/reason, encoding, FIFO and wire behavior remain intact.

Previously both anonymous live handlers stayed attached to a closed socket. If a caller retains that socket (for diagnostics, for example), its callbacks can retain the Relay and its event subscribers. This is an externally retained socket reference problem; ordinary unreachable cycles can still be garbage-collected. Structural listener inspection demonstrates the retention edge without making a measured heap-size or GC-timing claim.

Before the fix, two new controlled tests fail: final-close notification sees both live handlers still installed, and caller/listener isolation leaves extra library callbacks. A new real native WebSocket check also fails after a clean code-1000 close because one message handler remains instead of zero. The before-live receipt records failure and both disposable server processes still exit zero. The fix names the two existing callbacks so they can unregister themselves. It adds no AbortController, new public option or per-message branch; the message callback body and connect/send/request implementations remain byte-identical. Two removeEventListener calls run on final close. Listeners intentionally remain until that event, so local close still does not wait for the peer acknowledgement.

After the fix, all 22 mock connection tests pass. They cover removal before close notification, outstanding and queued controls rejecting without another send, caller-installed listeners surviving, and no subsequent Relay dispatch from deliberately injected late fixture events. Those synthetic events are robustness fixtures, not a claim that normal WebSockets deliver data after their final close event.
