# Keep deployment settings out of the JavaScript fixture — 2026-10-19

The JS checker owned its credentials, endpoints, worker count and idle timeout, but inherited other `WAR_*` deployment settings from the calling shell. The focused regression shows inherited admin-disable, admission and an unknown future setting reaching both child processes. A real run with `WAR_NO_ADMIN=true` fails before its JavaScript suite because the fixture's expected admin readiness listener is disabled.

The selected checker removes inherited `WAR_*` names in its own Bash process before building or launching fixtures, then applies the existing explicit fixture settings. It uses Bash's name-only prefix expansion and unset, without reading/logging potentially secret values. When executed normally, it cannot change the calling shell's environment. Unrelated build settings, including CARGO_TARGET_DIR, are preserved. No production relay, CLI configuration, protocol, workload limit or dependency changes.

The new controlled regression fails against the previous checker. Marker executables capture only dummy fixture values: the native process must receive exactly its intended test password and empty admin token; the bridge must receive no inherited `WAR_*` entries. The custom target and an unrelated sentinel must survive, and the supplied caller-environment dictionary must remain intact. Existing source-freshness/manifest guards continue to pass. All three regression methods (including the four earlier freshness subcases) pass in 0.813 seconds. Their fake processes open no listeners and their npm/curl stubs avoid network probes.

A separate fresh-source integration run supplies contradictory settings: no admin, a one-connection/one-channel limit, a one-byte output budget, an invalid allowed origin and an unknown deployment sentinel. The updated checker still passes all 65 protocol/legacy/idle checks in about 1.12 seconds and retires all six checked resource gauges. It uses the existing custom debug target and recompiles local sources through the freshness guard. Build/install/cleanup add wall time. `scenario.json` retains these nonsecret test settings; before/after logs are included.

This checker verifies its fixed disposable client-interoperability profile; it is not a way to validate caller-supplied production settings or a performance/population benchmark. Deployment-specific acceptance remains a separate task. Existing manual services, convenience binaries and unrelated dirty sources were preserved.

Run `python scripts/test-js-build-freshness.py` and `bash -n scripts/check-js.sh` for the fast checks. To repeat integration, execute the checker from the intended writable source tree with the recorded environment and a suitable custom Cargo target. Source, patch, original script and hashes are retained; `python docs/benchmarks/2026-10-19-js-fixture-environment/verify.py` audits saved evidence offline.
