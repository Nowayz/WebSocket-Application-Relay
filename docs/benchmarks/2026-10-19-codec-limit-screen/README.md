# Duplicate codec write-limit screen, 2026-10-19

Decision: retain the existing runtime and its cached FrameCodec write limits. Keep three focused public-API behavior tests. Source base `000d2fe`. No production protocol or native state-layout change is selected.

The candidate removes max_out_buffer_len and out_buffer_write_len from FrameCodec, which duplicate values already in WebSocketConfig. It removes the two private setters and their constructor/config-update calls. WebSocketContext passes its current config values on write; raw FrameSocket passes its existing unlimited/immediate defaults. No public API, payload owner, buffer allocation policy, framing, FIFO, quota or deadline changes. Native application output already bypasses this generic write-buffer path. Candidate code is retained in candidate.patch and full source files, not applied to the working implementation.

The prior selected release layout probe measures Connection=520, Stage=320, WebSocket=320 and Upgrade=288 bytes. A fresh clean release candidate probe measures 504/304/304/288 respectively. This removes 16 metadata bytes per connection record without adding an allocation. At the observed 131,072 slots, that arithmetic is 2 MiB of record storage; it is not measured resident memory, allocator footprint or a CPU prediction. Both build manifests pin exact source and binary identities. The candidate requires fresh:false recompilation. The existing selected control binary is reused, not described as rebuilt this turn. The control and candidate differ in two vendor sources plus cfg(test)-only registration/coverage.
