# Output-accounting review: avoid a duplicate counter-layout experiment

A fresh two-second profiled mixed fixture uses 64 private pairs, 2,048 fanout readers, four messages/window, four pinned native workers and eight pinned client workers on separate CPU sets. Inspection and churn are disabled. The profile passes body/FIFO, counter and resource-retirement gates with normal client/server exits and zero lost samples. The profiler is stopped with SIGINT (recorded exit -2) after capture, as intended by the harness. The executable is the frozen `worker-reservation-selected` native release; its startup error handling predates the later partial-thread cleanup fix, while the routing/output/metrics code being inspected is unchanged. The receipt retains the exact executable identity and commands.

Aggregated self user-cycle samples include connection driving (14.52%), private socket submission (7.85%), bounded receive/routing (6.65%), queued output (5.61%) and WebSocket reading (5.31%). Annotations cluster samples after delivery-counter and queue-credit atomic updates. Sampling skid and concurrent accounting make these clues, not precise instruction costs or proof of false sharing. Profiled timings are not ordinary performance results.

The proposed next candidate separated input publication, delivery counters and exact queue credit into 64-byte-aligned groups without changing public field types or atomic operations. It was compiled but **not timed or selected**. Further history review found this family of changes had already been tested: the 2026-10-16 padded/striped studies and the 2026-10-18 notification/counter-layout screen. Those comparisons did not establish a repeatable whole-workload advantage. The current profile supplies no new causal evidence to justify repeating that work. Native counter layout and output accounting remain unchanged.

The current performance guide now links all three prior accounting studies explicitly. It also distinguishes the historically rejected 2026-10-18 integer experiment from the later selected full-width inline integer implementation and its allocation/100k evidence. It lists the recent unselected observer-lock, queue-swap and boolean experiments, and includes the selected startup-failure fixes. This makes the current source decisions clearer without discarding older negative results.

## Scratch-directory recovery

During preparation, a reused `metrics-layout-work` name caused `mkdir` to fail, but the shell continued to archive extraction. This replaced historical scratch sources before the mistake was caught. The new sources were moved to the explicitly abandoned `metrics-layout-abandoned-20261019-work`, and all 112 files in the new build manifest were verified there. The historical scratch tree was reconstructed from its recorded `7877db4` base plus its archived candidate metrics source; all 108 expected files were compared byte-for-byte. Frozen historical executables, raw receipts and archived source/checksums were unchanged. The old study's verifier passes after recovery. No user source file or running service was touched.

The guide now explicitly requires a fresh snapshot directory and shell error propagation before archive extraction. The existing build helper rejects reused outputs, but cannot protect historical files from a preceding caller-side extraction. No new wrapper/tool is added to solve that shell-level mistake.

Raw perf data remains local at `artifacts/output-accounting-profile.perf.data`. The text report, annotations, receipt and recovery audit are retained here. Run `python verify.py` for the archived-evidence check. This review adds no runtime optimization, capacity result or latency claim.
