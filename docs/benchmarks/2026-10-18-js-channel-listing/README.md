# JavaScript channel-listing result validation

Selected: modern client opcode 2 acknowledgements must contain an array of two-element `[name_bytes, population]` rows. Names are decoded Uint8Arrays of at most 16 bytes. Population values must be nonnegative safe integer Numbers or unsigned uint64 BigInts. The guard returns the existing decoded result without converting counts or copying names; it adds no explicit per-row allocation or row-count quota. It executes only for channel-listing command results.

Previously `channels()` accepted arbitrary response values even though other management replies already had result guards. A malformed string, byte string, row shape or population could resolve to application code as a valid listing. It now follows the existing immediate rejection/error/application-Close-4002 path before resolving the pending command. Application payloads and the native relay are unchanged; this is a contract correction, not a performance claim.

The native format is checked before adding the guard: the real-server listing test already passes against the original client, while the malformed-result regression fails. The baseline full suite has 36 passes and that one failure. The real query authenticates a peer, checks a binary non-UTF8 channel with two members, an empty-name channel with one member, the persistent global channel, raw-byte name ordering, and exact self-routing afterward. No assumption is taken from a mock in place of the native encoder.

Twenty malformed values cover non-array listings, wrong row lengths, text/oversized names, negative/fractional/nonfinite/unsafe Numbers, out-of-range BigInts and nonnumeric populations. Five valid fixtures preserve empty listings, empty/binary/16-byte names, safe integers and uint64 BigInts. The guard validates semantic decoded values; it does not independently inspect CBOR wire tags or add a client-side sorting pass.

All 37 client tests pass in 1.097 seconds against disposable native/bridge servers, including existing real WebSocket fault peers, original legacy-client compatibility, native routing and idle policy. Final connection/session/queue/variable gauges are zero; both servers exit normally. The browser bundle rebuild succeeds in 7 ms, and Node syntax/diff checks pass. Existing manual services, native/C++ source overlays and convenience executables remain untouched; the browser bundle reflects the selected client source.

The patch applies to e92b266. Raw baseline/selected receipts retain frozen server/bridge identities, test commands, output and retirement gauges. Selected source and browser hashes are in build.json.
