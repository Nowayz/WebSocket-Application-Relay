# Live pressure checkpoint for short fanout tests

Selected tooling change: stability.py now accepts opt-in --fanout-teardown-gate, using the existing stress client's traffic_finished/continue handshake. The runner samples the live server before releasing healthy readers to teardown. The checkpoint must show exactly the requested number of unread-peer overloads and all expected healthy members. Final totals alone can include teardown-induced overload intent; they cannot locate pressure in the traffic phase.

No relay or stress-client runtime change is made. For gated runs, stdin is a pipe. Output lines use an unbuffered binary pipe, keeping selector readiness consistent with unread events; a buffered text wrapper can internally retain a next line that a file-descriptor readiness check cannot see. Gate polling reuses select rather than creating a selector descriptor each sample. JSON/error strings are decoded before storing them, preserving the receipt interface. Existing non-gated behavior stays opt-in-compatible with clients lacking the gate flag.

The live predicate requires slow-consumer count exactly equal to unread clients, joined session count equal to clients minus unread clients, and a TCP connection count between that healthy count and the original population. This distinction is real: the 1 KiB case has 62 live members but 64 TCP connections at the gate. Two retired unread transports still await Close completion. Requiring every descriptor to disappear immediately would conflict with the existing close policy. All final resources must still retire after teardown.

The selected-source confirmation holds 66 connections: one publisher, 61 fully validating readers and four unread peers. Four-message windows cycle 64-byte, 1 KiB and 64 KiB payload templates for two seconds. It verifies 1,355,420 healthy deliveries, all expected unique departure notifications and every full encoded body/order. At the gate there are exactly four overloads, 62 sessions/connections and zero charged queued bytes. No healthy teardown capacity Close occurs. The observed maximum is 4.273720 ms from window publication; it includes client/kernel/relay scheduling and is not a server-hop measurement or deadline guarantee.

Additional two-second gated runs check mixed sizes, fixed 1 KiB and a zero-unread control. All pass. The 1 KiB run verifies 2,457,812 healthy deliveries with four live overloads and 62 sessions; the healthy control verifies 1,511,380 deliveries with zero overloads and all 66 sessions retained. Intermediate mixed-size confirmations and the original non-gated case are retained as development evidence, not before/after performance comparisons. In total, the archived cases use 16 configured traffic seconds, with setup and checked teardown outside them. There is no 100,000-user or long-duration claim.

Every case uses the same frozen selected native binary and stress client, pinned by SHA-256 in the receipts. Native uses four workers within CPU mask 0-3; the client uses 8-11, disjoint physical cores on this host. These are process masks, not checked per-thread pins. Rates are disabled for stress; heartbeats retain server defaults. Fanout queue bytes are sized by the existing runner formula, max(1 MiB + 10, 32 * (largest payload + 20)). The global queue default remains unchanged. Recorded 250 ms samples are observations, not a continuous memory peak. Healthy completion, exact counters and final gauges demonstrate the finite checked case; they cannot prove every possible load or schedule.

Four focused unit tests validate accepted pending-Close transports, missing pressure, extra overload, missing healthy membership, impossible connection counts, the zero-pressure control and rejection of non-fanout gate calls. Existing one-second traffic/churn and two-second single-slow-consumer cases pass after the pipe interface change. Every application/server exits zero and no server requires forced kill. All final connection/session/queue/variable/read-storage/output-capacity gauges are zero, the root channel remains, and the fixed 1 KiB/traffic/churn/slow cases record zero routing copies. Mixed-size fanout deliberately exercises small-slice compaction: the final confirmation copies 3,932,374 of 485,851,396 routed value bytes (about 0.81%) once on ingress. The existing guard compacts a non-unique small view when its receive slab is larger than the base buffer and over eight times the message size, preventing a tiny queued body from pinning that slab. Fanout shares the resulting compact body; the copy count is not multiplied by recipients. Reused plus copied ingress value bytes exactly match the stress client's sent-value count. This bounded-retention policy is preserved. The raw receipts retain the existing working-tree source hashes separately from frozen binary hashes; those dirty source overlays were not used to rebuild the tested binary.
