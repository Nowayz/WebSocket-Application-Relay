# Report impossible worker reservations without panicking

`Config::validate` permits any positive worker count. Native startup then used `Vec::with_capacity(workers)` for worker storage and listener storage, which panics if the requested capacity cannot be represented. On this Linux x86-64 host, the existing native executable reproduces a `capacity overflow` panic and exit **101** with `--workers 18446744073709551615`.

Both startup vectors now use `try_reserve_exact`. Worker storage adds the error context `cannot reserve native worker storage`; listener storage returns an I/O error. The CLI now exits **1** with the capacity failure reported through its normal error path. The embedding API returns an error and releases the consumed listener. No arbitrary worker limit is introduced, and normal workers, queues, frame ownership, scheduling and per-packet code remain unchanged. This handles these two startup reservations; it does not claim that every allocation in the application is fallible or that OS overcommit cannot affect larger valid allocations.

The regression calls `serve` with `usize::MAX` workers and separately calls the listener-preparation helper with the same count. It checks that both return errors without unwinding, then binds each former address again to verify descriptor/port retirement. The impossible capacity is rejected before any worker threads start.

All **109 Rust library tests pass in 0.53 seconds** and Clippy passes with warnings denied. The freshly frozen native release reproduces the corrected CLI exit and message. In the clean source snapshot, the supported `scripts/check-js.sh` passes all **61 JavaScript protocol/legacy/idle cases in 1.119 seconds**, with all six checked resource gauges zero before fixture shutdown. It uses the custom Cargo target directory, exercising the newly corrected checker as well. Compilation and installation add wall time. No performance benchmark is needed or claimed for this cold-start error-path fix.

The prior selected control used for the panic reproduction is `artifacts/candidates/native-inline-u64/war-relay`; its startup reservation code matches the pre-fix source. Exact CLI arguments and the new executable hash are in `cli.json`; the build manifest and before/after/test logs are retained here. Existing manual services and the three pre-existing source overlays remain unchanged. Run `python verify.py` for the evidence audit.
