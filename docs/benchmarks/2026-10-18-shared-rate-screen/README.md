# Shared rate-configuration screen and retained policy tests

Rejected runtime change: removing cached rate values from each native connection shrinks the measured type layout, but the actual population-gate RSS does not improve and both candidate private maxima exceed both controls. Keep the existing connection-local rate cache. Retain four hand-calculated quota tests without changing production behavior.

The disabled-rate path already returns immediately, so there is no floating-point work to remove there. The candidate removes rates: [u64; 2] from RateLimiter and passes the two immutable Relay configuration values to allow() for each message. Tokens, timestamps, refill mathematics, debit order, disabled semantics, queue/body ownership and FIFO are unchanged. It adds no new pointer, allocation or runtime option. The measured test-build layout on this target changes from 48 to 32 bytes for RateLimiter and 520 to 504 for Connection. Multiplying the 16-byte type reduction by a live population is not an RSS or allocator-footprint measurement.

Control and candidate are fresh release builds from the same clean snapshot path, compiler, lockfile and Cargo target cache, with fresh:false required by build-snapshot.py. Each binary is frozen and SHA-pinned before traffic. cfg(test)-only layout/policy modules are present in diagnostic sources but not release code. Both complete source variants and build source-hash maps are retained. The user overlays are excluded.

A first four-process control/candidate/candidate/control screen runs private traffic with 64 clients, 1 KiB payloads, four native workers and two seconds/run. Native/client process CPU masks are 0-3 and 8-11; these are not verified per-thread pins. Every packet/sender/FIFO and final cleanup check passes, totaling 13,216,288 healthy deliveries. Candidate throughput is somewhat lower on average and ranges overlap; no CPU-speed win is established. Full receipts retain each process CPU/RSS sample and latency histogram.

The deciding full-population screen also uses control/candidate/candidate/control, two seconds/run. Each holds 100,000 private users in 6,250 rooms of 16 (four 1 KiB probes/user/second, eight observations each), plus 8,192 fanout readers, one authenticated protocol-census connection and one publisher offering four-message windows at 16 Hz. Inspectors, independent churn workers and additional pairs are explicitly zero. Eight native workers and both eight-worker clients are individually pinned to the existing disjoint physical CPU sets. The lightweight monitor keeps FD scans outside timed traffic. No profile, build or other workload overlaps timing. Rates are disabled equally; enabled-limit behavior is covered by the deterministic unit fixtures, not this population traffic. Loopback, no TLS.

All four population runs complete 32/32 windows and pass exact payload/FIFO/counter and final resource checks, with zero routing-copy counters. Every private user contributes eight samples and every fanout reader contributes 128; full per-user CSVs are retained, not a sample of users. Total checked population observations are 3.2 million private and 4,194,304 fanout. CPU spans the existing ready/measured gates including settling, not exactly two traffic seconds. RSS is a gated observation, not a continuous peak. Latencies include client/kernel/relay scheduling; the fanout measurement starts before reader notification and socket writes, not at an isolated server hop. Each user has too few observations for a long-term per-user p99 or latency SLA.

The candidate RSS is higher in both repeats despite the smaller type. The cause of that RSS difference is not isolated; type layout alone cannot account for process residency. CPU ranges overlap and private-user distribution quantiles are mixed, but the worst private observations are 4.32–4.71 ms for candidate versus 3.56–3.95 ms for control. This provides no reason to trade the current cache for the candidate. The current cache remains selected.

Selected change: src/server/rate_tests.rs and its cfg(test) module declaration. Hand-computed timelines check disabled limits, message-only fractional refill/burst caps, exact byte charging, and coupled-limit debit order after denial. They do not implement a duplicate token-bucket algorithm. The unchanged production runtime plus these four tests passes all 96 library tests in 0.50 seconds and Clippy with warnings denied. The experimental candidate separately passed 97 tests including its layout diagnostic. Run `cargo test --lib server::rate_tests` for just the four retained checks. The selected patch adds no production statements; removing its test-module declaration yields the original server source exactly.

Traffic phases total 16 seconds: eight small-screen seconds and eight full-population seconds. Population setup, CSV generation and exhaustive checked teardown add wall time. No multi-hour or default-enabled-rate population campaign was run. Existing manual services, convenience executables and the three pre-existing source overlays remain untouched. The latest native runtime stays selected.
