# Clean bridge failure and recovery when upstream is unavailable

Selected: a failed or timed-out upstream WebSocket connection now produces 1013 / Upstream Unavailable for the already-upgraded legacy client, using the existing bounded Close helper. Previously the connection attempt escaped through `?` and dropped the legacy transport without a Close frame. The original connection error is still returned for diagnostics after the Close attempt; internal upstream details are not put on the wire.

The existing ten-second connection timeout is preserved. A responsive legacy client can acknowledge and reach EOF immediately after rejection. The Close exchange has its existing separate ten-second bound and service cancellation still aborts the connection task. No retry loop, retry cache, public configuration, queue, new dependency or payload allocation is added to normal forwarding. Clients initiate subsequent attempts; the bridge can recover when its configured upstream returns.

A focused real-TCP regression binds an upstream port without listening, reserving the endpoint against other tests. It makes two legacy joins through a bridge limited to one admitted connection. Each must receive exactly 1013 / Upstream Unavailable, acknowledge and finish its Close. The same reserved upstream socket then begins listening. A third legacy join, without restarting the bridge or changing its URL, receives ID 42 and verifies a complete private CBOR/legacy payload exchange and clean Close. This guards both failure retirement and recovery. Against original runtime logic the first attempt fails in 0.00 seconds with ResetWithoutClosingHandshake. The selected clean snapshot passes all 114 library tests in 0.53 seconds and strict library/test Clippy.

The frozen release bridge is independently checked using the standard-library/raw-WebSocket controller archived here. Two real connection refusals receive the expected Close and EOF in about 4.22 ms and 0.41 ms. The same endpoint then accepts TCP but deliberately never answers the HTTP upgrade. The bridge reaches its real connection/handshake timeout, returns the same 1013 Close and EOF after 10.00187 seconds, and retires the stalled upstream socket. One bridge admission slot is reused across all three cases. Child descriptors return from 10 to 10 and SIGTERM exits zero. The ten-second case tests the real existing deadline rather than a test-only timeout setting. These are functional-check durations, not steady-state relay latency measurements.

The supported JavaScript checker passes all 61 native/CBOR/original relay.js/legacy/idle tests in 1.117 seconds, with no skips and all six checked resource gauges zero. Build/install/setup time is additional. Production services and convenience executables are not replaced. The clean snapshot excludes the three pre-existing dirty Rust/C++ source overlays.

The original/selected sources, exact patch, failing/passing logs, release controller/receipt, provenance and frozen build manifest are retained. Run `python verify.py` for an archived-evidence check. To rerun the release controller from the repository root, use `python docs/benchmarks/2026-10-19-bridge-upstream-unavailable/release-probe.py PATH_TO_BRIDGE FRESH_RECEIPT.json`; it imports scripts/reference.py and creates only its own disposable bridge/upstream sockets. Recovery after the endpoint begins listening is covered by the library real-TCP regression; the independent release probe covers refusals and the actual stalled-upgrade deadline. No large population or long soak is required for this connection-error correction.
