# Reject WebSocket text before typed-array size coercion

Selected: both JavaScript client receive paths require a binary WebSocket message before constructing the existing byte view. A shared decodeMessage helper rejects string input with a TypeError, then uses the unchanged Uint8Array/CBOR decode for binary data. Subscription welcome and established-connection replies both use it. Existing error handling rejects pending work and closes with browser-compatible application code 4002; queued commands cannot be sent once closing begins.

Previously new Uint8Array(event.data) ran before checking the WebSocket message type. The constructor treats primitive numeric strings as lengths: new Uint8Array('16').byteLength is 16. A short text frame such as '1048576' therefore selected an allocation request for a much larger zero-filled array before decoding failed. The regression intercepts that constructor call rather than allocating the requested buffer. This is a measured overload-selection defect, not a heap/RSS benchmark or a claim that the test exhausts memory.

Two controlled tests fail against the original client: one during welcome and one with a pending/queued control pair. A temporary constructor Proxy records string arguments and throws before allocation. Both old paths pass '1048576' to the constructor. After the fix neither does; welcome setup listeners retire, pending requests reject with the binary-CBOR type error, one Close is requested and a queued control never reaches the wire. The constructor is restored synchronously before awaiting test results. The mock socket keeps final Close separate from the local close request, as in the existing lifecycle tests.

Two additional real WebSocket cases send text welcome/control replies and verify actual code 4002 on the wire. The underlying peer uses the same numeric string, and validates masked short client frames and command count. Binary application strings remain encoded CBOR values inside binary frames. No valid binary API/encoding, command FIFO, ID behavior, dependency or server protocol changes. The binary receive path still creates the same ArrayBuffer-backed byte view; no additional payload copy is added.

Final supported clean-snapshot compatibility checking passes all 65 tests in 1.117 seconds (previous 61 plus four regressions), with no skips and all six final resource gauges zero. The snapshot excludes the three existing dirty native/C++ overlays. Focused source tests also pass 32 cases in 0.101 seconds before test-only readability cleanup; the final full suite covers the same final tests. Build/install/startup/cleanup add wall time. No multi-hour test or throughput campaign is required for this wire-boundary check.

The generated target/browser/relay.js is rebuilt. Its browser-target bundle passes all 32 focused lifecycle/protocol cases in 0.108 seconds, including the fake allocation guard and real WebSocket text/Close tests. Buffer is unavailable during module initialization to select cbor-x's browser Uint8Array allocation path, then restored for Node test tooling. These use Node WebSocket/EventTarget with the built browser module, not Chrome rendering acceptance. A fresh HTTP read from the existing local browser-check server on port 4180 returns status 200 and exactly the generated bundle SHA-256. Native/bridge manual services are not restarted or promoted.
