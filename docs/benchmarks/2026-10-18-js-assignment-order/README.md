# Publish acknowledged client identity before following messages

Selected: a validated opcode 3 acknowledgement updates `Relay.userId` synchronously in the message handler, before resolving its pending command. `assignId()` returns the acknowledged BigInt without a later state assignment. No optimistic update occurs before server acknowledgement; invalid replies retain the old identity and the existing protocol-error close behavior.

Previously the message handler only validated the acknowledged ID. The state update happened later in the async assignId wrapper after its await resumed. When a transport dispatched the next decoded frame in the same socket callback, application message handlers could observe the old userId even though the wire acknowledgement and sender ID already described the new identity. The server's FIFO and assignment were correct; client state publication lagged behind its incoming message dispatch.

Two deterministic checks reproduce the gap: a valid acknowledgement followed immediately by a message exposes the old identity, and a low-level request(3, ...) acknowledgement never updates identity. A real native-server test also fails against the original client: after authenticating, it starts assignment and pipelines a self-message to the known fixed ID without awaiting the acknowledgement. The received message has the new sender but its callback reads the old local userId. The baseline suite has 37 passes and these three failures.

The fix reuses the existing wireId validation result for the immediate state update. Low-level command results keep their original Number/BigInt representation; the high-level assignId result remains BigInt. Existing invalid-assignment tests confirm malformed/reserved acknowledgements reject without replacing identity. Command serialization, frame order, packet contents, timeout policy and native code are unchanged.

All 40 client tests pass in 1.107 seconds against the same frozen native/bridge binaries, including the pipelined native assignment and existing original-client compatibility, control guards, real WebSocket error closes, Close handshakes and idle policy. Both disposable servers exit cleanly and final connections/sessions/queued bytes/variable bytes are zero. The browser bundle rebuild succeeds in 7 ms, and syntax/diff checks pass. This is an asynchronous state-consistency fix, not a throughput or full-population latency claim.

The patch applies to 5eb7998. Raw original failures, complete before/after live receipts, selected source, browser/source hashes and test commands are retained. Native/bridge manual processes and the three protected dirty source files were preserved. The README/status guide describe the updated client guarantee.
