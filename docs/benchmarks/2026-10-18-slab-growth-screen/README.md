# Smaller large-arena growth screen, 2026-10-18

Decision: keep the existing runtime. Source base `623763e`. An isolated six-line admission-path candidate changes connection-slab growth from doubling to 1.5x whenever a full slab has at least 4,096 slots. Small slabs retain the library's original growth. It preserves geometric amortization, slot keys, compaction/reuse, socket owners, shared payloads, FIFO and resource limits, with no new runtime option. It can require more reallocations and can reserve more than the old policy at some population sizes; a smaller growth factor is not a universal capacity reduction. It is not selected.

The preceding matched Rust/C++ screen measured about 112 versus 60 MiB population-ready RSS. The current Connection layout is 520 bytes on this target (see the shared-rate diagnostic), and Slab grows its backing Vec geometrically. Spare metadata was therefore a plausible screening target, not a proven explanation of that entire RSS difference. Unused reserved pages may never become resident; capacity arithmetic is not RSS. The experiment explicitly measures the actual process rather than claiming bytes saved from the growth ratio.

The candidate compiles with fresh:false and passes all 96 clean-snapshot library tests in 0.49 seconds. Only src/server.rs differs from the committed snapshot. Its candidate.patch excludes all three protected working-tree overlays. The frozen control is the same selected production implementation from the preceding screen; its server source differs only by cfg(test) module declarations/diagnostics. The two build receipts pin every compiled source and binary. The existing control build is reused, not described as rebuilt this turn.

Two sequential fresh-process runs, control then candidate, use two traffic seconds each. They hold 100,000 private users in 6,250 rooms of 16 plus 8,192 fanout readers, a publisher and an authenticated census connection. Native and both clients use the same individually pinned eight-worker CPU sets and frozen client binaries. Private probes are four/user/second; fanout offers four-message windows at 16 Hz. Inspectors, independent churn and extra pairs are explicitly disabled. No profile, build, compression or other workload overlaps measured traffic. Loopback/plaintext, no TLS.

The candidate RSS is 2,036 KiB (1.77%) lower, far short of explaining the Rust/C++ memory gap. This is one pair, not a repeated confidence estimate; the CPU/latency differences do not establish a repeatable regression. They also give no demonstrated performance benefit to justify changing allocation policy. Consequently the experiment stops after this four-second traffic screen. No additional churn screen is needed to reject adoption; admission setup is observed, but long-term allocator churn is unverified. The existing simpler policy remains.

Both runs pass exact payload/FIFO/counter/census gates, all 32/32 offered fanout windows, and complete retirement. Each private user contributes eight observations, each fanout reader 128. Final connections, sessions, queues, variables, read reservations and output-queue capacity return to zero; routing copies are zero. All three child processes exit normally. The latency scope includes source-client/kernel/relay scheduling, not an isolated server hop, and these finite samples are not per-user long-term p99s or an SLA. CPU spans the existing gates including settling, not exactly two seconds; RSS is a ready-gate observation, not continuous peak. Setup is the capacity client's 100,000-user admission duration, not the extra fanout setup.

No production source, existing service or convenience executable was changed. Full per-user CSVs, exact wrapper commands, raw receipts, timelines, logs, patch and build identities are retained. Frozen executables remain at their original artifact paths and are SHA-pinned. Run `python3 verify.py` here for an offline evidence audit. The next memory experiment should first attribute retained allocations rather than infer them from a struct or reserved-slot count.
